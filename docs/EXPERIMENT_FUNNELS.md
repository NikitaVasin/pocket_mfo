# Воронки независимых экспериментов в AppMetrica

Цель: сравнивать дизайн, состав офферов, порядок и способ перехода по реальным показам и последующим конверсиям. Это контракт интеграции, а не подтверждение работы отчёта в живом кабинете AppMetrica.

## Распределение и композиция

Для каждого измерения заведите отдельную коллекцию: `screen_design`, `offer_placements`, `offer_order`, `dynamic_link_settings`. Новые эксперименты получают `distribution: independent`: стабильный hash пользователя и идентичности эксперимента → бакет 1…10000. Пользователь может иметь бакет 201 в одном тесте и 506 в другом. Повторный запрос не рандомизирует группу. Изменение границ допускает смену группы; закрепления прежних назначений нет. Прежние конфигурации без distribution сохраняют `shared`, пока вы явно не переключите их. Четыре независимых бинарных теста допускают все 16 сочетаний.

Каталог `partner_links` можно оставить общим для пользователей с нужными правами, а включение в экран и позицию задавать через размещения. Не включайте Variants на каталог только ради сортировки. Общая доступность офферов не означает снятия аутентификации, active и ViewRule. Для push используйте стабильную ссылку общего каталога; удалённый или выключенный оффер всё ещё может быть недоступен.

Один вариант по-прежнему имеет максимум один активный эксперимент. Универсального объединения нескольких патчей одного JSON и единого редактора аудиторий Push/Variants пока нет. Условия `variant` в Push используют тот же выбор группы; собственный язык остальных push-аудиторий сохраняется.

## Контекст показанного материала

Records API добавляет к записям Variants поле `variantContext`. Оно содержит назначение фактически возвращённого набора, ID записи, ревизию публичного материала, версию конфигурации и подписанный token. Сохраняйте контекст вместе с моделью, которая действительно отрисована. Если ограничиваете Records API параметром fields, включите variantContext. Загрузка, prefetch, `/variants/me` и история назначений не являются показами.

Для составного экрана соберите контексты всех применённых измерений и передавайте один и тот же список в шаги воронки. Если поменялась модель экрана — получите новые контексты и запишите новый показ. На сервере допускается до 30 контекстов; конфликтующие назначения одной коллекции отклоняются. Token действует 24 часа; после истечения обновите контент. Он привязан к пользователю, не заменяет права доступа и не отправляется в AppMetrica. Выданный контекст подтверждает происхождение материала, а не добросовестность клиентского события показа.

Пример для `pocket_mfo_flutter` (контексты берутся из уже загруженных записей):

```dart
final shown = [
  for (final record in [designRecord, placementRecord, orderRecord, openingRecord])
    if (VariantExposure.fromRecord(record) case final exposure?) exposure,
];

// После появления экрана. Защита от повторов из build() — обязанность UI.
await mfo.reportEvent('screen_view',
    parameters: {'screenId': 'home'}, exposures: shown);

// При фактической видимости конкретного оффера, не всех загруженных офферов.
await mfo.reportEvent('offer_impression',
    parameters: {'screenId': 'home', 'linkId': linkId, 'position': position},
    exposures: shown);

// В обработчике нажатия; блокируйте повторное нажатие до завершения resolve.
await mfo.reportEvent('offer_tap',
    parameters: {'screenId': 'home', 'linkId': linkId, 'position': position},
    exposures: shown);
final result = await mfo.resolvePartnerLink(linkId: linkId, exposures: shown);
await mfo.reportEvent('offer_link_ready',
    parameters: {'linkId': linkId, 'clickId': result.clickId}, exposures: shown);
if (context.mounted) await result.link.open(context);
```

Ошибка отправки некритичной аналитики не должна навсегда блокировать действие пользователя: обработайте её в прикладном слое. Resolve может вернуть 400 для некорректного/просроченного контекста. Для контекста `dynamic_link_settings` изменение набора, версии или содержимого даёт 409: обновите и перерисуйте экран, затем зафиксируйте новое действие. Это предотвращает приписывание нового способа открытия старому тесту. Проверка выполняется в одной транзакции с применением политики и сохранением клика. Контексты старого дизайна/порядка сохраняют силу для ещё показанного материала; доступность ссылки проверяется заново.

Параметры SDK и серверных событий:

- `experiments`: имя коллекции → `variant/experiment/group`, либо ключ варианта без теста;
- `attributionBasis: content_exposure` при переданном контексте;
- `exposures`: ID контекста, collection, record, revision, set, version, без token;
- `linkId`: оффер, `clickId`: выданная ссылка, доступен после resolve;
- `profile_id`: один и тот же PocketBase user.id в SDK и Post API.

Без контекста сохраняется обратная совместимость: SDK использует кеш `/variants/me`, сервер — все текущие подходящие конфигурации автоматически. Это `current_assignment`. Не смешивайте его с `content_exposure` при оценке фактических показов. При явных контекстах непоказанные эксперименты не добавляются автоматически. Поэтому для оценки переходов нужен и контекст openingRecord.

## События и построение отчёта

| Шаг | Событие | Источник / смысл |
| --- | --- | --- |
| Экран | `screen_view` | Приложение: появился экран |
| Оффер | `offer_impression` | Приложение: конкретный оффер видим |
| Нажатие | `offer_tap` | Приложение: действие пользователя |
| Выдана ссылка | `offer_link_ready` | Приложение: необязательный шаг для связи с clickId |
| Переход | `offer_click` | Сервер: GET редиректа, не подтверждение загрузки сайта |
| Заявка | `offer_lead` | Постбек партнёра lead |
| Холд | `offer_hold` | Постбек партнёра hold |
| Одобрение | `offer_approved` | Постбек партнёра approved |
| Отказ | `offer_rejected` | Постбек партнёра rejected |

Для сравнения A/B создайте одинаковые воронки и фильтры шагов по `experiments.<collection>` и `attributionBasis = content_exposure`. Пример: `screen_view → offer_impression → offer_tap → offer_click → offer_approved`. Отдельно анализируйте путь через lead/hold: партнёр может сразу прислать approved, а плагин не придумывает отсутствующие промежуточные события. Отказ — альтернативный исход, а не шаг после одобрения. Revenue — отдельный денежный поток выбранного статуса, не замена событию `offer_approved`.

[AppMetrica описывает воронки из 1–10 шагов с фильтрами по параметрам событий](https://appmetrica.yandex.ru/docs/ru/data-collection/about-events). Не считайте, что UI автоматически связывает каждый показ и approved по равенству произвольного clickId: это нужно отдельно проверить в выбранном отчёте. Для точной аналитики по заявке используйте clickId в выгрузке/собственном расчёте; в стандартном пользовательском отчёте один профиль может иметь несколько показов и заявок. Перед resolve clickId ещё нет: показ связывается с выдачей через exposures и linkId, а не через заранее выдуманный clickId.

При смене группы один пользователь может участвовать в нескольких вариантах в разные моменты. Сохранённый контекст исключает переатрибуцию старой конверсии, но не устраняет повторное участие пользователя при статистическом сравнении. Фиксируйте период, окно конверсии и единицу анализа; для новой гипотезы меняйте ключ эксперимента. Смена текста внутри группы сохраняет ключ группы, но меняет revision: разные материалы можно отделить через exposures или новую гипотезу. Независимое распределение не исключает взаимодействия эффектов дизайна и порядка.

SDK и сервер должны относиться к одному приложению AppMetrica. [Post API объединяет данные с SDK по profile_id/device_id; синхронизация не мгновенная](https://appmetrica.yandex.ru/docs/ru/mobile-api/post/about). [Ограничения Post API](https://appmetrica.yandex.ru/docs/ru/mobile-api/post/restrictions) требуют известного SDK профиля; назначению в единственной первой сессии может потребоваться следующая сессия. События старше допустимого окна нельзя передатировать ради успешного импорта. Проверка настоящего устройства и кабинета остаётся обязательной перед экспериментом.

## Повторы конверсий

Бизнес-статус заявки и результат доставки — разные состояния. Нельзя просто пропускать approved в таблице: запись могла сохраниться до неудачной отправки. Теперь отдельно хранятся подтверждения каждого статуса и единственного Revenue по заявке. HTTP 200 от AppMetrica отмечает доставку; повтор не отправляет подтверждённую часть. Если событие прошло, а Revenue явно отклонён, повторяется только Revenue с первоначальными timestamp и суммой. Изменение revenueStatus/суммы не повторяет уже подтверждённый доход.

Сетевой обрыв/таймаут даёт `unknown`: AppMetrica могла принять запрос. Автоматического повтора нет; после внешней сверки используется Go `ReconcileDelivery`. Старые конверсии без квитанций также требуют сверки. Это ограничение, а не exactly-once. В Revenue передаётся стабильный transaction_id=clickId, но документация [параметров Revenue](https://appmetrica.yandex.ru/docs/ru/mobile-api/post/post-revenue) не служит гарантией серверной дедупликации. Изменение суммы/возврат требуют отдельной политики корректировок.

Клики по повторному GET всё ещё могут повторяться; не открывайте URL предварительно для проверки. Очереди восстановления потерянных кликов нет. Следовательно, сбор воронки поддержан контрактом, но отсутствие потерь при отказе внешнего API не гарантируется.

## Приёмка интеграции

1. На одном тестовом устройстве получить SDK-профиль и четыре контекста экрана, записать фактические показы и нажатие.
2. Проверить одинаковые experiments/exposure IDs в SDK и сохранённом clickData, одинаковый profile_id; token не должен попасть в SDK-логи.
3. Изменить распределение после показа: для старого материала сохранить прежнюю атрибуцию; смена применяемой политики перехода должна потребовать обновления.
4. Получить реальные lead/hold/approved, повторить постбек и проверить отсутствие второго подтверждённого статуса/Revenue. Отдельно проверить явный отказ и неизвестный исход.
5. Дождаться обработки в AppMetrica и проверить фильтры и знаменатели воронки; тесты репозитория используют HTTP-заглушку и этого шага не заменяют.


## Проверки реализации, 23.09.2026

- Полный `go test -race ./...` и `go vet ./...` прошли; после последних изменений Partner Links его race-тесты пройдены повторно.
- 83 Dart/Flutter-теста и `fvm flutter analyze` прошли без замечаний.
- `npm ci`, установка Chromium и 78 Playwright-тестов прошли, включая обе темы.
- Docker smoke прошёл при повторном запуске с диагностикой. Первый запуск завершился unhealthy до готовности PocketBase; первопричина не установлена. Оба временных Compose project очищены штатным скриптом.
- Проверены все 16 комбинаций четырёх тестов, совпадение SQL/API/Go/Push-выбора, совместимость shared, подделка/смена пользователя/истечение контекста, сохранение группы после смены распределения, отказ устаревшей политики перехода без побочных записей, повторные/конкурентные постбеки и неопределённый сетевой исход.
- Живой кабинет AppMetrica и мобильные устройства не проверялись. После этого прогона добавлен отдельный плагин Typed Config с формами и сборкой проекций; его актуальный контракт и проверки описаны в plugins/typedconfig/README.md.
