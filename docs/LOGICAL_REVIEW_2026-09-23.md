# Согласованность плагинов и независимые эксперименты

Дата: 23 сентября 2026. Проверено рабочее дерево, включая незакоммиченные изменения Push и новый `currencyrates`.

Цель пользователя: независимые одновременные тесты дизайна, офферов, порядка и переходов.

> Это исходное ревью до исправлений. Актуальные изменения и границы: [воронки](EXPERIMENT_FUNNELS.md), [предложение по экранным конфигурациям](SCREEN_CONFIG_DESIGN.md).

## Вывод

Набор покрывает основу персонализированной витрины. Однако текущая модель Variants не обеспечивает независимость параллельных экспериментов, а цепочка аналитики не гарантирует привязку конверсии к фактически показанной версии контента. Для поставленной цели нужны изменения модели экспериментов и интеграционного контракта. Переписывать остальные плагины оснований нет.

Это ревью исходников, существующих Go-тестов и отдельного воспроизведения на временной базе. Успех тестов не означает полноту продуктового функционала.

## Покрытие

| Компонент | Что покрывает | Существенная граница |
| --- | --- | --- |
| Variants | Сегменты, выбор набора, диапазоны групп, история наблюдавшихся назначений | Общий бакет; один активный эксперимент внутри варианта; одно решение на коллекцию |
| Singleton | Настройки/страница: максимум одна запись на набор | Не гарантирует наличие записи и не создаёт содержимое |
| Polymorphic Relation | Типизированная ссылка на запись одного из нескольких типов; права и удаление | Не конструктор страницы и не поиск эквивалентной записи в доступном наборе |
| Dynamic Link | Режим открытия, предупреждения, общая политика по Variants | Политика разрешается по актуальному состоянию; нового Flutter-компонента не создаёт |
| Partner Links | Выдача ссылки, сохранение заявки и назначений, постбеки, Revenue | Нет очереди доставки/дедупликации событий; список коллекций для снимка задаётся вручную |
| Push | Устройства, сегменты, кампании, расписание, очередь и атрибуция открытий | Собственный язык аудиторий; фиксированная цель сообщения; отчёты кампаний не заменяют анализ A/B |
| MCP | Ограниченное редактирование контента и инструменты Push | Нет готовых инструментов публикации/предпросмотра/анализа экспериментов Variants |
| Schema Lock | Схема управляется кодом; редакторы меняют контент и настройки Variants | Новые типы контента/поля требуют миграций; блокировка не проверяет целостность витрины |
| Currency Rates | Импорт курсов, история и очистка; подключён в example и тестовый стенд | История накапливается с подключения без загрузки пропущенных дней; интеграции с расчётами Revenue нет |
| Flutter-фасад | Гостевая авторизация, профиль аналитики, события, ссылки, push | Не реализует универсальную сборку витрины и журнал фактических показов |

## Находки по приоритету

### 1. Блокер цели: эксперименты зависимы друг от друга

[`Bucket`](../plugins/variants/types.go#L96) зависит только от auth-коллекции и пользователя. [`compileConfig`](../plugins/variants/config.go#L284) использует тот же бакет во всех коллекциях и экспериментах.

При одинаковом делении 50/50 дизайн A всегда сочетается с офферами A, дизайн B — с офферами B. Раздельный вклад изменений определить нельзя. Разные границы не создают независимых распределений автоматически.

Воспроизведено на временном PocketBase: четыре коллекции, четыре теста 50/50, 256 пользователей. Получено только `AAAA: 118`, `BBBB: 138`; остальные 14 сочетаний отсутствуют.

Кроме того, второй активный эксперимент внутри одного варианта явно запрещён ([config.go](../plugins/variants/config.go#L313)). Отказ и сохранение прежней версии конфигурации подтверждены тем же воспроизведением.

Нужно: независимый детерминированный выбор по идентификатору эксперимента и пользователю; явные слои взаимоисключения для конфликтующих тестов. Для намеренно согласованных изменений нескольких коллекций — общий идентификатор одного эксперимента. Нельзя просто заменить существующий бакет: это перераспределит действующих участников.

### 2. Высокий приоритет: назначение не равно фактическому показу

[`PocketMfo`](../packages/pocket_mfo_flutter/lib/src/pocket_mfo.dart#L419) отдельно получает `/api/variants/me`, сохраняет только карту строк `experiments` и прикладывает её к событиям. Загрузка контента не связана с этой картой одним снимком. [`Partner Links`](../plugins/partnerlinks/api.go#L87) заново вычисляет назначения при выдаче ссылки.

Сценарий: пользователь увидел витрину A; изменились условия сегмента или конфигурация; пользователь нажал на прежнюю карточку. Сервер может сохранить уже B, тогда как клиентское событие ещё содержит A. При недоступности прежней ссылки возможен отказ вместо перехода. После выдачи ссылки снимок для постбеков действительно зафиксирован — эта часть реализована и протестирована корректно.

История Variants фиксирует наблюдавшиеся решения, включая `/me`, а не отрисовку экрана. Карта аналитики также не содержит `Version`; редактирование содержимого набора не создаёт отдельную ревизию экспериментального материала.

Нужно: контракт фактического показа с идентификатором эксперимента, группой, версией материала и идентификатором показа; связь показа, клика и конверсии. Сервер должен проверять такой контекст, а не доверять произвольной группе из клиента. Для продуктовых событий полезно различать актуальные назначения пользователя и назначение конкретного показанного элемента.

### 3. Высокий приоритет: стабильный бакет не фиксирует участие

[`compileConfig`](../plugins/variants/config.go#L332) каждый раз выбирает группу по текущим границам, а вариант — по первому актуальному совпадению аудитории. Переход 50/50 → 80/20 переводит бакеты 5001–8000 из B в A. Изменение профиля или связанных данных может перевести пользователя в другой вариант.

Для персонализации это ожидаемая семантика. Для эксперимента, где участие должно сохраняться, её недостаточно.

Нужно явно выбрать политику: фиксировать назначение при вступлении либо запрещать изменение распределения действующего эксперимента и создавать новую версию. Отдельно определить поведение при потере соответствия аудитории.

### 4. Высокий приоритет: наборы не складываются и не наследуют содержимое

У записи одно поле `content_set`, у коллекции одно эффективное решение. Тест состава каталога и тест порядка того же каталога не накладываются друг на друга как независимые изменения.

Пустая группа скрывает даже заполненный Default. Воспроизведение: одна базовая запись, выбранная пустая экспериментальная группа — пользователю доступно ноль записей. Singleton сохраняет гарантию «не больше одной», но допускает ноль.

Связи содержат конкретные ID. Если страница ссылается на запись другого недоступного набора, штатные правила корректно скроют её при expand; автоматической замены на вариант этой записи нет. Публикация отдельной конфигурации атомарна, но готового админского релиза нескольких коллекций с проверкой всей страницы нет. Из Go несколько операций можно объединить внешней транзакцией.

Предлагаемая прикладная модель: общий каталог офферов и отдельно экспериментальные размещения/ранжирование; настройки дизайна и открытия — отдельные независимые параметры. Для страниц из разных типов блоков можно использовать коллекцию упорядоченных размещений с Polymorphic Relation на один блок. Нужна проверка заполненности обязательных наборов и доступности связей перед включением эксперимента.

### 5. Высокий приоритет для метрик: повторная доставка не идемпотентна

[`postback`](../plugins/partnerlinks/postback.go#L175) сохраняет конверсию, затем отправляет событие и, при соответствующем статусе, Revenue. Повтор успешно обработанного постбека снова выполняет отправку. При частичном успехе и повторе возможны дубли; без повторов при ошибке транспорта возможен пропуск в аналитике.

Текущий контракт прямо допускает отдельное событие на повторный запрос. Это не неожиданная регрессия, но ограничение пригодности необработанных сумм событий/Revenue для выбора победителя. Уникальная запись заявки в SQLite не делает внешнюю отправку идемпотентной. Новые Push-отчёты считают некоторые события по уникальному clickId, но суммирование Revenue от этого автоматически не становится уникальным по заявке.

Нужно: определить единицу конверсии и правила исправления статусов/сумм, хранить идентичность события, очередь доставки и раздельное состояние доставки события/Revenue. Не обещать exactly-once при неоднозначном результате внешнего запроса; предусмотреть сверку.

### 6. Средний приоритет: нет единого контракта состава экспериментов и сегментов

Клиентский `/me` возвращает решения по всем подходящим коллекциям; Partner Links берёт только [`Options.VariantCollections`](../plugins/partnerlinks/types.go#L21). Новый тест может появиться в клиентских событиях, но отсутствовать в снимке конверсии, если его забыли добавить в серверные Options.

В текущем example список содержит `demo_offers` и `dynamic_link_settings`, при этом `demo_offers` привязан к `demo_members`, а Partner Links и Flutter-витрина работают с `users` и `partner_links`. Поэтому пример не доказывает сквозную работу экспериментов над реально отображаемыми офферами.

У Push свой тип Condition и свои сохранённые аудитории. Он умеет фильтровать конверсии и относительное время, а Variants использует другую модель связей и операторов. Аудиторию Push нельзя непосредственно выбрать как аудиторию витрины. UI Variants исключает системные коллекции, включая `conversations`, из обычного выбора связей. Готового общего конструктора поведенческих сегментов нет.

Нужно: единый источник состава экспериментов для аналитики и явный общий контракт сегмента либо серверные признаки пользователя, которыми пользуются оба модуля. Не обязательно объединять весь SQL-компилятор двух плагинов.

### 7. Средний приоритет: цель push не согласована с доступностью вариантов

[`validateMessage`](../plugins/push/store.go#L240) проверяет у действия `partner` длину ID. Кампания сохраняет один ID для всех получателей. Выбор получателей не проверяет ViewRule этой ссылки для каждого пользователя. Сам Partner Links проверяет доступ корректно и отказывает, если ссылка недоступна.

При вариативных `partner_links` широкая рассылка может привести часть пользователей на недоступное предложение. Между отправкой и открытием пользователь также может сменить сегмент.

Нужно: переход по стабильному бизнес-ключу с разрешением доступной версии либо проверка кампании и согласованная аудитория, плюс обработка исчезнувшей цели на клиенте.

### 8. Отдельная конкретная проблема: токен в исходниках

В [`example/main.go`](../example/main.go#L33) после чтения окружения есть резервное строковое значение, похожее на OAuth access token. Поэтому пустая переменная окружения фактически не отключает токен, хотя README описывает именно такое поведение.

Убрать резервный секрет из исходников. Если значение настоящее, отозвать/заменить его и проверить попадание в историю Git. Действительность токена и удалённый репозиторий в этом ревью не проверялись; значение здесь не воспроизводится.

## Что согласовано

- Variants ограничивает выбор стандартными API rules до пагинации; Partner Links дополнительно проверяет ViewRule при resolve.
- Singleton опирается на индекс БД и согласует его с `content_set`; тесты покрывают оба порядка регистрации и откаты.
- Polymorphic Relation использует штатные relations и права expand. Его применение к владельцу конверсии не требует публичного обхода защиты.
- Dynamic Link используется и как самостоятельное поле, и через Apply в Partner Links.
- Schema Lock оставляет рабочие API плагинов и закрывает произвольное изменение схемы. MCP редактирует разрешённый контент через Records API с хуками.
- Push отделяет запуск от сетевой доставки, сохраняет очередь и проверяет поколение привязки устройства. Источник конверсии фиксируется через callback Partner Links.

## Приоритет развития

1. Спроектировать независимые назначения и слои конфликтующих экспериментов; сохранить совместимость действующих распределений.
2. Ввести подтверждённый контекст показа и сквозную атрибуцию. Добавить метрики показов, кликов, заявок и дохода с определёнными знаменателями.
3. Разделить каталог, размещения, ранжирование и параметры дизайна. Определить композицию независимых изменений и поведение при конфликте.
4. Добавить проверяемую публикацию: заполненность, связи, версии материала, предварительный просмотр, включение и откат.
5. Сделать доставку конверсий устойчивой к повторам; затем строить сравнение групп, проверку распределения и статистическую оценку результата.

Полноценный новый плагин для каждого пункта не обязателен: основная работа относится к Variants, Partner Links и Flutter-контракту витрины. UI сможет переключать только те компоненты и режимы, которые заранее реализованы в приложении.
