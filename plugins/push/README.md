# Push-кампании

Go-плагин PocketBase для устройств, аудиторий, сохранённых кампаний и очереди отправки через AppMetrica Push API. Вкладка **Пуши** встроена в штатную админку. Schema Lock остаётся включённым.

```go
bridge := mcp.Register(app, mcp.Options{ContentCollections: []string{"offers"}})
push.Register(app, push.Options{AuthCollections: []string{"users"}, MCP: bridge})
// Для атрибуции Partner Links:
partnerlinks.Register(app, partnerlinks.Options{
    AuthCollections: []string{"users"},
    Attribution: push.Attribution,
})
schemalock.Register(app)
```

Регистрация до Bootstrap/Start. Сначала подключите Polymorphic Relation, Variants, Singleton и Dynamic Link, если они используются. Порядок регистрации Push и Partner Links между собой несущественен; auth-коллекции должны существовать при Start. `MCP` опционален.

## Первое подключение

1. В AppMetrica настройте отправителей Firebase/APNs и нативный Push SDK в приложении.
2. Задайте настройки через Go-код (см. ниже) или, если поля не закреплены, в «Пуши → Настройки» задайте Application ID, OAuth token и скорость отправки 100–5000 сообщений/с. Пустое поле OAuth сохраняет текущий токен. Токен хранится в служебной коллекции без шифрования на уровне плагина, не выдаётся через UI/Records API/realtime. Защитите доступ к базе и бэкапам.
3. Во Flutter включите `registerDevices: true` в `PocketMfoPushConfig`. Пример уже использует этот параметр. Серверный OAuth token в приложение не передаётся.
4. Создайте кампанию и выберите «Все пользователи» либо создайте и выберите аудитории. Сохранение **не запускает** отправку. Сначала сохраните кампанию, проверьте аудиторию и отправьте тест на выбранные устройства.
5. «Запустить рассылку» создаёт отдельный запуск. Можно указать время; пустое время означает сейчас. Очередь обрабатывается каждую минуту.

## Настройки через Go-код

```go
applicationID, sendRate := int64(6361870), 1000
oauthToken := os.Getenv("APPMETRICA_PUSH_OAUTH_TOKEN")
push.Register(app, push.Options{
    AuthCollections: []string{"users"}, MCP: bridge,
    OAuthClientID: "8e1f79cf905d4a70b30507ea80e0730f",
    Managed: &push.ManagedConfig{
        ApplicationID: &applicationID, OAuthToken: &oauthToken, SendRate: &sendRate,
    },
    LockAdminConfig: true,
})
```

Так настроен `example/main.go`; Docker Compose передаёт `APPMETRICA_PUSH_OAUTH_TOKEN` из окружения. После задания переменной перезапустите сервер (для Compose пересоздайте контейнер). Пока она пуста, рассылки недоступны, но регистрация устройств работает.

`Managed` фиксирует переданные непустые указатели; указатель на пустую строку отключает токен, даже если ранее он был сохранён в базе. Значения копируются при Register. Закреплённые поля нельзя переопределить через Configure, HTTP или MCP. Остальные поля редактируемы. `LockAdminConfig` дополнительно запрещает все изменения настроек через HTTP, включая суперпользователя; доверенный Go-код может менять незакреплённые поля. UI показывает недоступные поля и причину блокировки.

Токен из Go/окружения не сохраняется в базе; прежний сохранённый токен остаётся неактивным до снятия закрепления. Несекретные эффективные ID и скорость сохраняются при Configure. Application ID также фиксируется при запуске, чтобы изменение кода при следующем запуске не обошло защиту существующих устройств/незавершённых рассылок. При конфликте сервер завершает запуск с ошибкой, данные не изменяются.

`Options.OAuthClientID` задаёт публичный ClientID Яндекс OAuth в коде и добавляет ссылку «Получить OAuth-токен» в настройки. Client secret для используемого implicit flow не требуется и не хранится. Полученный access token по-прежнему задаётся через `APPMETRICA_PUSH_OAUTH_TOKEN`.

OAuth получают по [официальной инструкции](https://appmetrica.yandex.ru/docs/ru/mobile-api/intro/authorization): создайте OAuth-приложение через указанную там специальную ссылку, добавьте `appmetrica:read` и `appmetrica:write`, получите токен с его ClientID. Этот ClientID отличается от Application ID `6361870`. Авторизуйтесь аккаунтом с доступом к приложению. Значение передавайте только серверу в переменной окружения.

Application ID, клиентский SDK API key и серверный OAuth token — разные значения. Для регистрации нужны авторизованный пользователь, включённый `registerDevices`, инициализированный нативный SDK и его Device ID; серверный OAuth не требуется. Web/preview регистрацию не выполняет. Разрешение хранится отдельно в `notificationPermission`; отказ дополнительно выключает `enabled`. Flutter синхронизирует статус после запроса разрешения и при возвращении приложения на экран.

## Устройства

`POST /api/push/devices` принимает `id`, `secret`, `deviceId` (числовой `appmetrica_device_id` для API, полученный как SDK `DeviceIdHash`), `platform` (`android`/`ios`), `language`, `appVersion`, `enabled`, `notificationPermission` (`notDetermined`, `denied`, `deniedPermanently`, `authorized`, `provisional`; отсутствие значения — `unknown`). Пользователь и auth-коллекция берутся только из авторизации. `id` и случайный 43-символьный `secret` установки сохраняются клиентом до первого запроса; повтор после потери ответа использует те же данные. В базе только хеш секрета.

Повторное присвоение существующей установки требует её секрета. Один AppMetrica Device ID не может принадлежать двум записям. При смене аккаунта/разрешения меняется поколение привязки: подготовленные задания для прежнего владельца исключаются перед отправкой. Устройство нельзя отозвать из уже принятой AppMetrica отправки. Нативный ID остаётся клиентскими данными; endpoint не выполняет аппаратную аттестацию устройства.

`POST /api/push/devices/disable` с `id`/`secret` отключает привязку. Фасад вызывает его перед выходом/сменой аккаунта и ожидает результат; при сетевой ошибке смена через фасад не продолжается, чтобы не оставить активной старую привязку. Прямая работа с authStore вне фасада должна самостоятельно соблюдать этот порядок. При смене аккаунта фасад повторно регистрирует ту же установку.

На старте и при возвращении в приложение обновляются разрешение и активность. После ручного запроса разрешения можно вызвать `mfo.refreshPushDevice()`. Клиент получает API ID через `AppMetrica.requestStartupParams([AppMetricaStartupParams.deviceIdHashKey])` → `result.deviceIdHash`; обычный `AppMetrica.deviceId` возвращает другой, шестнадцатеричный идентификатор и для Push API не подходит. Это различие описано в [FAQ AppMetrica](https://appmetrica.yandex.ru/docs/ru/troubleshooting/troubleshooting). Ожидание ограничено 10 секундами; при отсутствии ID ошибка передаётся в `PocketMfo.onError`, следующий возврат в приложение повторяет регистрацию. Версия приложения берётся из `AppMetricaConfig.appVersion`; задайте её для сегментации по версии. Web push не поддерживается.

## Аудитории

При создании и редактировании охват пересчитывается автоматически после паузы в 400 мс: число подходящих пользователей из всей выбранной auth-коллекции, процент и количество устройств. Пользователь с несколькими устройствами учитывается один раз. В числитель входят только пользователи с доступными включёнными устройствами; знаменатель включает также пользователей без устройств. Для пустой базы показывается 0%. HTTP/MCP `audience_preview` дополнительно возвращает `totalUsers`; подсчёт выполняется одним SQL-запросом и ничего не сохраняет. Кнопка «Обновить подсчёт» запускает проверку вручную.

Хранятся отдельно от групп AppMetrica. Включение нескольких аудиторий в кампанию — объединение; исключения вычитаются; устройство не дублируется. `userIds`/`deviceIds` ограничивают выборку ручным списком, `excludeUserIds` исключает пользователей. Все условия дополнительно требуют включённого устройства и существующего пользователя.

Типизированное дерево условий:

```json
{
  "kind": "all",
  "children": [
    {"kind":"field","source":"device","field":"platform","op":"eq","value":"android"},
    {"kind":"field","source":"device","field":"lastSeen","op":"withinHours","value":336},
    {"kind":"not","children":[
      {"kind":"conversion","children":[
        {"kind":"field","source":"conversion","field":"status","op":"eq","value":"approved"}
      ]}
    ]}
  ]
}
```

- Группы `all`, `any`, `not` (у not один ребёнок); максимум 6 уровней/100 узлов.
- `field`: source `user`/`device`/`conversion`; операции `eq`, `ne`, `gt`, `gte`, `lt`, `lte`, `empty`. Для дат — `withinHours` и `olderHours` с числом часов.
- `conversion`: существует одна заявка текущего пользователя, удовлетворяющая вложенному дереву. Все условия проверяются в одной строке. `not` вокруг conversion означает отсутствие такой заявки. Данные берутся из Partner Links, с учётом его очистки по TTL.
- `variant`: `collection`, `variant`, `experiment`, `group` — текущее эффективное назначение по decision view Variants. Учитываются пользователи с сохранённым `content_bucket`. Пользователи, созданные до подключения Variants, получают его при следующем авторизованном запросе; до этого в такую аудиторию не входят. История назначений не изменяется.
- SQL не принимается; поля и значения проверяются по схеме. JSON, секреты и произвольные переходы по связям не поддержаны.

Опция «только последнее активное устройство» выбирает последнее включённое устройство пользователя в целом; если оно не входит в аудиторию, более старое не подставляется. Интервал рассылок считается от резервирования устройства в запуске, включая неопределённые/неудачные отправки; это консервативный лимит частоты. Тестовые запуски обходят аудитории/лимит и не меняют его.

## Кампании и очередь

В кампании можно выбрать **«Все пользователи»** без создания аудитории. Это пользователи всех подключённых в `Options.AuthCollections` auth-коллекций, у которых есть включённые устройства. Удалённые пользователи, отключённые устройства и неподключённые коллекции не входят в рассылку. Исключения аудиторий, выбор последнего устройства и интервал рассылок продолжают применяться. Сохраните кампанию, нажмите «Проверить аудиторию», затем «Запустить рассылку».

В HTTP/MCP укажите `allUsers: true` и пустой/отсутствующий `audienceIds`. Для выбранных аудиторий используйте `allUsers: false` (по умолчанию) и непустой `audienceIds`; неоднозначный запрос с обоими режимами отклоняется. Пустой список сам по себе никогда не означает рассылку всем. Старые кампании сохраняют прежнюю семантику. При запуске по расписанию режим фиксируется в снимке кампании, а список доступных устройств определяется в момент обработки расписания.

Настройки/аудитории/кампании используют optimistic version. Изменение устаревшей версии отклоняется. Кампания содержит заголовок, текст, HTTPS-изображение и действие: открыть приложение, маршрут или запись Partner Links. JSON действия формируется автоматически.

В админке партнёрская ссылка выбирается через штатный select с поиском по названию, провайдеру и ID. Список загружает активные предложения; ранее сохранённый ID отключённой/недоступной ссылки остаётся видимым. Ошибка загрузки допускает повтор без потери черновика.

Запуск хранит снимок сообщения, условий аудиторий, Application ID и скорости. У запланированного запуска фактические получатели выбираются в момент обработки расписания; у немедленного — атомарно при создании запуска. Поэтому редактирование сохранённой кампании не меняет уже созданные запуски. Расписание хранит абсолютное время; отправка по локальным часовым поясам устройств пока не предусмотрена.

Очередь сохраняется в SQLite: задания по 10 000 устройств, максимум 10 заданий/проверок статуса за проход и 50 секунд на проход. Выборка, резервирование и повторная проверка владельцев выполняются пакетами SQL. AppMetrica берёт на себя отправку в FCM/APNs. `send_rate` ограничивает скорость каждой группы AppMetrica; несколько одновременных запусков имеют отдельные группы.

`idempotencyKey` обязателен для запуска: повтор с теми же параметрами возвращает существующий запуск, с другими — ошибку. Перед внешним запросом задание сохраняет `client_transfer_id` и статус `unknown`. После сбоя/перезапуска сначала проверяется статус. Неопределённый запрос **не повторяется автоматически**, даже если проверка пока не находит его. Это избегает слепых дублей, но может потребовать решения оператора о новой рассылке. Явный 429 откладывает повтор; другие явные ошибки 4xx (кроме 408) завершают задание отказом. Exactly-once доставки не обещается.

Отменить можно только будущий запуск со статусом `scheduled`. AppMetrica-отправки после передачи отменить через этот плагин нельзя. `sent` означает завершённую отправку провайдером, а не доказанную доставку на устройство.

## Конверсии

Для каждого запуска создаётся отдельная группа AppMetrica со стабильным именем, tag равен ID запуска. Повтор после потери ответа создания группы сначала ищет существующую группу. Группа доступна в push-отчёте AppMetrica; её ID отображается в результатах.

При нажатии Flutter передаёт `/api/push/open` ID запуска и токен из payload вместе с секретом установки. Сервер проверяет пользователя, поколение привязки и наличие устройства в снимке отправки. Открытие идемпотентно по паре запуск/устройство. Тестовые открытия не участвуют в атрибуции.

`partnerlinks.Options.Attribution: push.Attribution` сохраняет `clickData.push = {campaignId, runId}` при выдаче партнёрской ссылки. Правило: последнее зарегистрированное открытие за 7 дней, до выдачи ссылки; для пуша конкретного предложения учитывается только это предложение. Для маршрута/открытия приложения учитывается последующий переход к любому предложению. Источник сохраняется в конверсии и передаётся с существующими событиями/Revenue Partner Links. Позднее одобрение не меняет источник.

В боковой панели результатов метрики загружаются только из AppMetrica Reporting API через серверный OAuth. «Этот запуск» отбирает события по `clickData.push.runId`, «Вся кампания» — по `clickData.push.campaignId`; группы доставки берутся из снимков реальных запусков (тестовые исключены). Локальные записи используются для идентификаторов и периода, не для значений метрик. Период — с создания первого выбранного запуска до текущего дня UTC. Удаление конверсий из PocketBase не уменьшает показатели AppMetrica.

- Доставка/показ/открытие: уникальные устройства `ym:pc:*Devices`, фильтр по группам запусков; показ — Android. Для расширенной статистики iOS требуется Notification Service Extension, которой нет в базовом Flutter-пакете.
- Этапы: `ym:ce2:uniqParamValues{'clickData.clickId'}`, группировка по `conversion.status` с включением неопределённого значения (событие редиректа). Считаются уникальные выданные ссылки, не люди. Повтор этапа для одной ссылки не увеличивает его счётчик. Это независимые этапы за период, не строгая последовательная воронка и не текущие статусы: одна ссылка может встречаться в разных статусах. Одобрение не синтезирует отсутствующий lead. Отношение одобрений к lead показывается только при ненулевом знаменателе и результате ≤100%.
- Доход: `ym:r2:inappRevenueRUB` и `ym:r2:purchases`, только `one_time_purchase` с соответствующей атрибуцией. Суммы по `approved` и `hold` разделены; валюты пересчитывает AppMetrica в RUB. Это переданный revenue, а не подтверждённая выплата или прибыль за вычетом расходов. Включите `SendRevenue` у провайдера Partner Links. Повторные постбеки создают повторные revenue-события; последующий отказ не отменяет ранее переданную выручку.

HTTP `POST /api/push/admin/analytics` / MCP `push_analytics` принимают `{"runId": "…", "scope": "run"}` (`scope`: `run` по умолчанию, либо `campaign`). Доступ только суперпользователю / ключу с этим инструментом. Кэш процесса: 5 минут, при ошибке раздела — 30 секунд; не более 32 отчётов. Обновление панели до истечения кэша не расходует квоту API. Смена OAuth инвалидирует кэш. Каждый раздел имеет статус и ошибку: неполные ответы и ошибки API не заменяются нулями. Показаны время получения, задержка и признак семплирования. Для общей доставки с фильтром групп длиннее 4000 символов показана недоступность, доход/этапы остаются доступны. При ограничении периода со стороны API показана ошибка, диапазон молча не сокращается.

В списках кампаний и истории «Результаты» открывает только диагностику сервера, без обращения к AppMetrica. Отдельная кнопка «Результаты AppMetrica» открывает панель аналитики.

Вкладка «Обзор» сравнивает до 10 последних кампаний с реальными (не тестовыми) группами отправки и временем запуска не позднее конца выбранного периода. Учитываются и события за выбранные даты от более ранних отправок; список не ограничен последними 100 запусками интерфейса. Период задаётся явно в UTC (1–90 дней), есть пресеты 7/30/90 дней, переход на предыдущий/следующий интервал, перетаскивание графика и стрелки клавиатуры для сдвига на день. Легенда скрывает линии; таблица сравнения и раскрываемые дневные данные остаются доступны.

`POST /api/push/admin/analytics_overview` / MCP `push_analytics_overview` принимает `{"dateFrom": "2026-09-01", "dateTo": "2026-09-23"}`. Четыре агрегатных запроса Reporting API получают доставки по группам/дням, этапы по кампании за весь период и отдельно по дням, revenue по кампании/дню/статусу. Push в обзоре использует **события** (`sentEvents`, `receivedEvents`, `openedEvents`), чтобы корректно складывать повторные запуски; в индивидуальной панели остаются уникальные устройства. Уникальные ссылки за период не вычисляются суммой дневных уникальных значений. Revenue суммируется по дням; hold отделён. Идентификаторы групп сопоставляются по `id`, а не по названию. При неполном/слишком большом ответе раздел недоступен, значения не подменяются нулями. Кэш обзора — до 16 периодов, 5 минут (30 секунд при ошибке); OAuth и состав кампаний входят в ключ.

`push_report` сохраняет прежние локальные поля `opens`/`conversions` для совместимости API; UI не использует их как аналитику. Статусы очереди, ошибки пакетов и размер снимка остаются серверной диагностикой. Атрибуция описывает связь после открытия пуша, не причинный эффект рассылки. Данные AppMetrica поступают с задержкой; отсутствие события не подтверждает отсутствие действия.

## MCP и HTTP

Инструменты: `push_fields`, `push_audiences`, `push_audience_save`, `push_audience_delete`, `push_audience_preview`, `push_campaigns`, `push_campaign_save`, `push_campaign_delete`, `push_preview`, `push_launch`, `push_test`, `push_runs`, `push_report`, `push_analytics`, `push_cancel`. Выдавайте `push_launch` отдельно от подготовки контента. Ключ с инструментами Push имеет административный доступ к этим операциям во всём подключённом приложении; коллекционные ограничения MCP относятся только к `content_*`.

Админка использует те же доменные операции: `GET /api/push/admin/state`, `PUT /api/push/admin/config`, `POST /api/push/admin/{action}` (имя без `push_`). HTTP admin требует superuser; секреты и служебные записи нельзя менять штатным Records API, batch, truncate или через MCP-контент.

Проверки: Go race, права обычного пользователя/суперпользователя, откат, потеря ответа, смена владельца, атрибуция, обе темы браузера и Flutter mocks. Настоящую доставку проверьте на устройстве с настроенными AppMetrica/Firebase/APNs; автоматические тесты используют заглушку.

Контракт провайдера: [отправка сообщений](https://appmetrica.yandex.ru/docs/ru/mobile-api/push/post-send-batch), [проверка статуса по clientTransferId](https://appmetrica.yandex.ru/docs/ru/mobile-api/push/get-status-group-id).

### Диагностика отправки

В истории запусков статус показан цветной меткой с подписью. «Результаты» содержат причину последней ошибки, статусы отдельных пакетов, число устройств, `transferId`, `client_transfer_id` и время следующей проверки. HTTP-ошибки сохраняют код и диагностические сообщения AppMetrica; асинхронный `failed` — причины из `transfer.errors`. Секреты и снимки получателей в отчёт не включаются.

Для старых неудачных запусков без сохранённой причины кнопка «Запросить причину в AppMetrica» восстанавливает её по идентификаторам отправки (до 20 пакетов за запрос). Тот же вызов доступен через MCP `push_refresh_report` с `runId`. Он только проверяет статус, не отправляет пуш повторно. Если AppMetrica уже не хранит отправку, восстановить детали нельзя.

Пакет содержит сообщения только для платформ его получателей: Android-рассылка не требует настроенного отправителя iOS. Статус «Отправлена» обозначает завершённую отправку в AppMetrica, а не подтверждение доставки на устройство.

### Разрешения и интерфейс

В рассылку входят только устройства с `enabled=true` и разрешением `authorized` или `provisional`. Фильтр применяется к аудиториям, выбору последнего устройства, тестовым запускам и повторно перед отправкой. Изменение разрешения обновляет поколение привязки: ранее подготовленный снимок не отправляется после отзыва разрешения, даже если его затем выдали снова.

При обновлении сервера поле добавляется автоматически и атомарно. Существующие устройства получают `unknown` и не участвуют в отправке до синхронизации обновлённым клиентом. Для самостоятельного `PushDevices.sync` передавайте фактическое `notificationPermission` из `AppMessaging.getPermission()`; значение по умолчанию — `notDetermined`.

Кампании отображаются карточками. Создание и редактирование открываются кнопками в штатном боковом диалоге PocketBase; несохранённые изменения требуют подтверждения при закрытии. Результаты запуска открываются отдельным боковым диалогом из карточки кампании или истории. Аудитории также отображаются карточками; условия, ручные списки и актуальный охват доступны в боковом редакторе с закреплённой кнопкой сохранения. Устройства доступны в системной коллекции `push_devices` для просмотра и фильтрации, включая разрешение уведомлений. Редактирование привязок выполняется только через клиентский API.

Удаление доступно в боковом редакторе сохранённой кампании или аудитории с подтверждением. HTTP `campaign_delete` / `audience_delete` и MCP `push_campaign_delete` / `push_audience_delete` принимают `{ "id": "...", "version": 1 }`. Версия проверяется внутри транзакции: устаревший редактор не может удалить изменённую запись. Кампания удаляется только после завершения всех запусков (статусы `sent`, `failed`, `empty`, `cancelled`); историю, снимки, открытия, атрибуцию и аналитику удаление не затрагивает. Для запланированной рассылки сначала доступна отмена. Аудиторию нельзя удалить, пока она есть в получателях или исключениях любой сохранённой кампании; сообщение указывает одну из таких кампаний. Проверка ссылок атомарна с сохранением кампании. Удалённые определения восстановить через интерфейс нельзя.
