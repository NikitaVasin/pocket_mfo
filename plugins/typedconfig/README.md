# Typed Config

Типизированное поле `typedConfig` для экранных конфигураций PocketBase. Администратор видит карточки элементов и формы, а приложение получает упорядоченный JSON-список. JSON-редактора в интерфейсе нет.

## Подключение

```go
import "github.com/NikitaVasin/pocket_mfo/plugins/typedconfig"

variants.Register(app) // если нужны эксперименты
// До Bootstrap / Start; повторный Register безопасен.
typedconfig.Register(app)
```

Плагин самостоятелен: Variants, Singleton и Polymorphic Relation не обязательны. Работает через штатный Records API, поэтому Schema Lock не требует новых разрешений. Схема задаётся Go-миграциями; пользовательские данные редактируются формами. HTTP-запись конфигураций, включая удаление, разрешена только суперпользователю и дополнительно подчиняется стандартным API rules.

Пример схемы (сначала сохраните коллекцию offers):

```go
c := core.NewBaseCollection("screen_configs")
c.ListRule = types.Pointer("@request.auth.id != ''")
c.ViewRule = types.Pointer("@request.auth.id != ''")
c.Fields.Add(&typedconfig.Field{
    JSONField: core.JSONField{Name: "items", Help: "Блоки экрана"},
    Schema: typedconfig.Schema{
        Version: 1,
        Definitions: map[string]typedconfig.Node{
            "title": {Kind: "string", MaxLength: 150},
        },
        Types: []typedconfig.Block{
            {Key: "heading", Label: "Заголовок", Fields: []typedconfig.Property{
                {Name: "text", Label: "Текст", Required: true,
                    Node: typedconfig.Node{Ref: "title"}},
            }},
            {Key: "offer", Label: "Карточка оффера", Fields: []typedconfig.Property{
                {Name: "offer", Label: "Предложение", Required: true,
                    Node: typedconfig.Node{
                        Kind: "reference",
                        Source: &typedconfig.Source{
                            Collection: offers.Id,
                            Mapping: map[string]string{"title": "name", "linkId": "id"},
                        },
                        Fields: []typedconfig.Property{
                            {Name: "title", Label: "Название", Required: true, Node: typedconfig.Node{Kind: "string"}},
                            {Name: "linkId", Label: "Ссылка", Required: true, Node: typedconfig.Node{Kind: "string"}},
                        },
                    }},
            }},
        },
    },
})
if err := app.Save(c); err != nil { return err }
```

Рабочая миграция с заголовком, оформлением, оффером и вложенными вопросами: [демо](../../example/migrations/1789948808_demo_typed_configs.go). В example откройте **demo_screen_configs → Главная витрина**.

## Типы и формы

- `string`: текст, необязательный MaxLength; `number` / `integer`: число с Min/Max; `boolean`: переключатель; `enum`: выбор из Options.
- `object`: вложенная группа Fields; `array`: карточки элементов типа Items (до 100).
- `Ref`: именованный тип из Definitions, включая объекты и списки; циклы и неизвестные имена запрещены.
- `reference`: выбор записи в штатном PocketBase picker с поиском. Источник фиксирует коллекцию, а не позволяет автору произвольную коллекцию.
- `Property.Required`: обязательное значение; пустая строка недопустима. Необязательное поле включается отдельным переключателем.

На верхнем уровне до 100 блоков, у каждого стабильный ID, type и data. Дублирование создаёт новый ID, перестановка сохраняет прежний. Карточки сворачиваются, есть поиск, кнопки выше/ниже и перетаскивание за заголовок. Вложенные списки редактируются формами. Сохранение, отмена и черновики используют штатную форму PocketBase. Схема типов отображается только для ознакомления; визуального конструктора самих схем пока нет.

Сервер отклоняет неизвестные свойства/типы, дубли ID, неверные значения, отсутствующие источники и слишком глубокие структуры. Ограничения: 256 KiB на поле, 30 типов блоков, 100 именованных типов, ограниченная глубина и число узлов. Корневое поле должно быть необязательным: каскадное удаление последнего источника может оставить пустой список.

## Хранение и связи

Запись редактируется атомарно одним Records API запросом. В поле хранится список с явными ссылками:

```json
[
  {"id":"heading1","type":"heading","data":{"text":"Предложения"}},
  {"id":"offer1","type":"offer","data":{"offer":{"id":"offer0000000001"}}}
]
```

Для каждой коллекции-источника создаётся скрытое настоящее relation-поле `tc_*`, содержащее все зависимости этого поля конфигурации. Это обеспечивает согласованность JSON и связей без отдельных запросов сохранения каждой карточки. Не изменяйте служебные поля вручную. Сервисные поля скрыты даже в ответе суперпользователю; HTTP-запись напрямую или модификаторами запрещена.

Удаление исходной строки удаляет **весь верхнеуровневый блок**, содержащий ссылку на неё, в том числе внутри вложенного списка. Остальные блоки и их ID сохраняются. Удаление блока не удаляет общий источник. Удаление и обновление зависимых записей происходят в одной транзакции из HTTP, Go и SaveNoValidate; ошибка откатывает всю операцию. Удаление коллекции-источника запрещено, пока она объявлена в схемах: сначала явно мигрируйте схемы.

Здесь выбран нативный вариант хранения: JSON-поле + реальные служебные relations. Отдельной таблицы screen_items нет. Конфигурации сохраняются целиком; при большом числе экранов учитывайте стоимость поиска зависимостей по массивам связей. Между параллельными авторами действует обычная семантика Records API PocketBase — отдельного optimistic-lock протокола для записей плагин не добавляет.

## Mapping и чтение приложением

Mapping сопоставляет свойства результата с полями источника. Разрешены явно типизированные скалярные поля и select; JSON, custom fields, relations, скрытые поля и traversal не принимаются. На сохранении схемы имена коллекций/полей нормализуются в ID: переименование поля-источника не ломает mapping. Удаление, сокрытие или несовместимая смена типа источника отклоняются. Изменение значения источника, нарушающее требования уже сохранённых проекций, тоже откатывается.

Обычный пользователь/гость через Records API получает готовые значения:

```json
{"id":"offer1","type":"offer","data":{"offer":{"title":"Предложение","linkId":"offer0000000001"}}}
```

Без Mapping результат ссылки — `{id, collectionId}`. Суперпользователь получает исходные ссылки для редактирования. ViewRule источника проверяется отдельно: если источник недоступен, весь зависимый блок исключается из ответа. `nil` и пустое правило сохраняют штатную семантику PocketBase. Источниками могут быть другие несистемные base-коллекции; auth/view и ссылка на собственную коллекцию запрещены.

Проекция вычисляется при чтении и не копируется в хранимый контент. Изменения источника видны в следующем ответе. Уже открытое приложение должно обновлять данные: изменения источника не создают отдельный realtime update родительской конфигурации; при удалении блоков родитель действительно обновляется. Специального endpoint, произвольного SQL/JavaScript или query-source нет.

## Variants и AppMetrica

Публикуйте конфигурацию Variants на обычной коллекции с этим полем. Singleton при необходимости ограничит её одной записью на набор. В пользовательском ответе `variantContext` подписывает уже собранное публичное содержимое: изменение отображаемого источника меняет revision. Исторический контекст показанного материала сохраняет прежнюю атрибуцию.

Дизайн, размещения, порядок и политику перехода можно хранить отдельными конфигурациями. Приложение явно собирает экран и передаёт контексты всех использованных записей в события и resolve. Плагин не угадывает правила объединения конфликтующих слоёв и не отправляет показ при загрузке. Общие офферы удобнее хранить вне Variants; если источник сам участвует в независимом тесте, отдельно передайте контекст его показанного набора. См. [воронки](../../docs/EXPERIMENT_FUNNELS.md).

## Dart

`GenerateDart(writer, schema, "Home")` генерирует dependency-free DTO для собранного ответа. Используйте схему из `field.Schema` после сохранения/загрузки. Генератор создаёт sealed HomeItem с вариантами и вложенные immutable классы, проверяющие типы при декодировании. Суффикс Value у getters предотвращает конфликты с ключевыми словами Dart; суффикс числа у классов — коллизии имён. Это модели ответа приложения, не формат сохранения ссылок в админке.

```go
if err := typedconfig.GenerateDart(writer, field.Schema, "Home"); err != nil {
    return err
}
```

Использование на стороне Dart: `HomeItem.fromJson(itemJson)`, далее pattern matching по сгенерированным вариантам. [Сгенерированный пример](testdata/models.dart) и [исполняемая проверка](testdata/smoke.dart).

При изменении схемы увеличивайте Version. Все существующие записи проверяются внутри транзакции; несовместимая публикация отклоняется без частичных изменений. Для изменения структуры сначала выполните совместимую миграцию данных. Генерацию Dart и обновление Flutter-компонентов выполняйте вместе с изменением схемы. Неизвестный новый type старое приложение отвергнет: планируйте совместимость клиентских версий.

## Проверки

`go test -race ./plugins/typedconfig`, `npx playwright test typedconfig.spec.js`, `fvm dart analyze plugins/typedconfig/testdata`, `fvm dart run plugins/typedconfig/testdata/smoke.dart`.

Проверяются вложенная валидация, права, скрытые поля, изменения/удаления источников и откат, schema rename, Variants revision, типизированные Dart DTO, карточки в обеих темах и при Schema Lock. Flutter-рендерер произвольных новых компонентов, визуальный дизайнер схем и полноценный preview приложения не входят в плагин.
