# Variants: инструкция для агента

Используйте для выбора набора контента по аудитории и стабильному бакету пользователя. Это распределение контента и история наблюдавшихся назначений; плагин не вычисляет конверсии и статистическую значимость эксперимента. Полная документация — [README.md](README.md).

## Как подключать

1. `variants.Register(app)` до Bootstrap / Start.
2. Создайте обычную коллекцию контента и несистемную auth-коллекцию. Задайте исходные ListRule/ViewRule целевой коллекции в миграции.
3. Вызовите `Publish(app, Config{Collection: "offers", AuthCollection: "users", ...})` с `Version: 0` для первой настройки. Она наследует правила коллекции и переводит существующие записи в Default.
4. Для изменений загрузите конфигурацию через `Load`, измените её и передайте в `Publish`, сохранив текущую Version. Публикация атомарна; устаревшая версия отклоняется. Не публикуйте заново при каждом старте без необходимости.
5. Клиент читает контент стандартным Records API. Администратор управляет вариантами из самой коллекции; Schema Lock оставляет отдельное окно Variants.

```go
cfg, err := variants.Load(app, "offers")
if err != nil {
    return err
}
cfg.Experiments = false
_, err = variants.Publish(app, *cfg)
return err
```

`Load` возвращает `sql.ErrNoRows`, если коллекции/конфигурации нет. `Resolve` вычисляет решение; `Bucket(authCollectionID, userID)` — стабильный бакет. `/api/variants/me` и `/me/history` дают пользователю его назначения; админский preview не записывает историю.

## Инварианты и сопровождение

- Служебные коллекции: `pv_configs`, `pv_sets`, `pv_states`, `pv_history`; view `pv_choice_*`; поля `content_set`, `content_bucket`; индексы `idx_pv_*`. Управляйте ими только через API плагина. Одного экспорта схемы недостаточно для переноса конфигурации.
- `content_bucket` принадлежит Variants только у auth-коллекции из опубликованной конфигурации. Одноимённое поле посторонней коллекции не должно меняться при Register, Save, авторизации или HTTP-запросе.
- Бакет в диапазоне 1…10000 стабилен. Ноль означает отсутствие назначения. Создание/изменение контента разрешено только суперпользователям; бакет не заменяет авторизацию.
- Наборы не наследуют Default. Ключи вариантов/экспериментов/групп стабильны; изменение имени сохраняет набор, изменение ключа создаёт другой. Архивирование не удаляет записи и историю.
- Условия компилируются из типизированного дерева. Вложенные условия `exists` должны относиться к одной связанной строке. Не принимайте произвольный SQL от клиента.
- ListRule/ViewRule сочетаются с выбором набора. Сохраняйте различие `nil` и пустого правила. После настройки правила меняйте через Publish, а не прямым сохранением сгенерированной схемы.
- `LockAdminRules(app)` включает необратимую на уровне публичного API политику для HTTP. Schema Lock вызывает её автоматически. Подмену базовых правил проверяйте внутри транзакции до любых записей. Программный `Publish` должен сохранять возможность изменять базовые правила.
- Первое подключение наследует исходные правила даже при Go Publish. Для другого исходного доступа задайте правила коллекции до подключения; последующие изменения доступны через загруженный Config.
- История описывает наблюдавшиеся решения, не фактические показы. Realtime использует штатную проверку прав; изменение аудитории само по себе не обновляет список на клиенте.
- Основные файлы: `config.go` — публикация/схема, `conditions.go` — компилятор, `plugin.go` — хуки, `api.go` — решение/история/HTTP, `admin_policy.go` — запрет редактирования правил.

Проверки: `go test -race ./plugins/variants ./plugins/singleton ./plugins/schemalock` и `npx playwright test variants.spec.js singleton.spec.js schemalock.spec.js`. Сохраняйте проверки границ бакетов, same-row exists, конкурентной публикации, отката, изоляции auth-коллекций и защищённого режима.
